## 真实网络样本

- 单视频：[Brooklyn Nets 公开帖子](https://x.com/BrooklynNets/status/1349794411333394432)，来自 yt-dlp 官方提取器测试样本。实际下载 270P H.264/AAC MP4，2,664,147 字节，约 324.5 秒；经 FFprobe 确认视频及音轨保留，随后通过正常视频库入口加入播放墙并实际播放。
- 多视频：[Prime Video UK 公开帖子](https://x.com/primevideouk/status/1578401165338976258/video/2)，来自官方双视频样本。解析显示两个视频，分享链接默认选中第 2 个；选中视频单独下载成功并入库。
- 测试使用直连网络、独立临时应用目录与下载目录。测试完成清理样本与下载组件，不向用户真实视频库写入测试条目。
- 远程封面由受限后台获取为本地数据，下载页面没有放开任意远程资源加载。

原始结果位于 `test-results/downloads-results.json`、`test-results/desktop-results.json`（均为忽略的本地测试产物）。

## 本轮修正的问题

1. 下载设置草稿误携带保存目录，被后台白名单拒绝：改为只提交连接方式、代理和自动入库选项。
2. Electron fetch 的 manual 重定向会取消官方组件下载：改用独立 Session 检查初始及重定向请求，再由其处理正常重定向。
3. 下载器未提供的速度/总大小字段会输出 `NA`，导致进度 JSON 无效：明确使用 `null` 占位，只输出需要的进度字段。
4. 任务完成与自动入库间缺少反馈：将入库进度独立显示，失败后仅重试入库，不重复下载。
5. 下载临时文件可能被文件夹扫描提前发现：临时目录使用 `.vexa-downloads` 并从递归扫描中排除；成功验证后才发布最终文件。

## 用户本地试用

双击项目根目录 `启动本地测试.cmd`，或运行 `npm run test:local`。需要本机现有 Node.js 与已安装的项目依赖；脚本只编译并启动桌面应用，不打包。测试配置单独保存在 `.cache/local-test-profile`，首次启动为空库，已安装版本的数据保持独立。

打开左侧“下载” → 安装组件 → 选择保存位置 → 粘贴帖子链接 → 解析 → 选择视频和画质 → 开始下载。连接 X 不成功时，在“下载设置”中选择实际可用的系统代理或手动代理。首次安装组件也使用该设置；组件可从页面上的官方发布页获取后手动导入指定版本。

默认下载后入库，不自动播放。关闭测试窗口时有任务会提示停止；清除任务记录不会删除已完成的视频。下载任务不跨重启保存，保存位置与连接偏好会保存。

## 仍需验证与功能限制

- 真实 HTTP(S)/SOCKS5 代理服务器、复杂系统 PAC、多种受限网络条件未完成端到端验证；当前网络实测使用直连。代理输入校验与参数传递已接通。
- 用户主动 X 登录及本机 Cookie 文件导入已接通，补充验证见下；真实受限账号内容、地区/年龄限制仍需用户授权后的样本验证。短链接、直播、外站视频、整账号批量下载不在支持范围。
- 不支持跨重启续传或持久化下载记录；正常取消/退出清理当前任务临时文件。断电遗留临时目录可在退出应用后手工清理，不会进入视频库。
- 本机真实进程树取消已测；尚未在大量不同 X 媒体形式、文件系统、外接盘和长时间多路播放叠加下载下完成压力验证。
- macOS 与 Windows ARM64 未实测；当前组件启用范围为 Windows x64 / macOS，后者仅准备固定官方组件信息，不宣称兼容性通过。
- X 的访问规则可能变化。官方提取器存在及本轮样本成功，不代表所有公开链接始终可下载；本轮不提供任意版本组件更新。

完成用户本地验证后再决定版本号、打包和发布。

## “明明有视频”误报修复与登录补充（2026-10-19）

用户提供的链接已复现：默认 GraphQL 返回 `TweetTombstone`，没有视频信息和具体原因；syndication 同样未提供视频，旧接口返回 404。未使用用户账号，因此不能据此确认帖子已删除、确切需要登录或确实没有视频。此前直接翻译成“没有可下载的原生视频”属于误报，现改为访问/登录/兼容性可能性说明，并对歧义无媒体失败尝试一次备用解析。

- 新增“连接 X”：独立官方登录窗口；实际网络已加载出 X 的用户名登录表单，但未输入或操作任何真实账号。
- 新增“其他方式 → 导入 X 登录文件”：只取 X/Twitter 域的 auth_token/ct0；拒绝过期、跨站、缺字段和换行注入，凭据不进入界面或任务记录。
- 增加 9 项单元/集成检查，当前总计 **94 项、12 个文件通过**：含备用解析、限流不滥重试、登录参数作用范围和凭据文件生命周期。
- 独立桌面授权测试使用合成测试值验证：真实 OS 加密、不将凭据发送给渲染页、重启本地恢复、断开清除、登录窗口沙箱及捕获完成关闭。原始结果位于 `test-results/x-auth-results.json`。模拟值不用于证明真实账号授权或用户链接下载成功。
- 原有 16 项真实公开样本下载检查在修复后再次通过，包含单视频、多视频第 2 条的下载入库与实际播放。
- 真实用户登录后的该链接解析/下载尚未验证，需要用户在应用中主动登录后重试；不把增加登录入口表述为该链接已下载成功。

## 密码提交后“出了点问题”的兼容修正（2026-10-19）

截图是 X 的通用失败页，未给出具体错误原因，不能据此认定密码不正确。代码和匿名网络复查发现以下问题：

1. 登录 Session 默认 User-Agent 带应用名和 Electron 标记。现仅对该 Session 去除这两个应用标记，保留本机实际 Chromium 版本及系统信息，不改其他页面。
2. 资源白名单实际拦截了 X 登录页引用的 `accounts.google.com` 与 `appleid.cdn-apple.com` 脚本。已补充这两个确切主机；匿名真实网络复查已不再出现这两个脚本的拦截，仍拦截无关遥测。
3. 旧的跳转检查将所有框架的重定向统一按顶层 X 域名限制，可能中断 Arkose 等嵌入验证页面。改为区分主页面和子框架：主页面保留 X/Twitter 限制，子框架允许现有可信验证域。权限和沙箱继续启用。

新增可展开的登录连接诊断，仅显示已知服务名称、HTTP 状态或标准网络错误码，最多 8 项，不存储请求网址、参数、正文、密码或 Cookie；关闭登录窗口后仍可查看这次的状态，新一轮登录和断开连接时清空。不能由 HTTP 403 等状态反推出密码错误。

“其他方式”增加“在浏览器打开 X”，固定打开官方登录地址。使用系统浏览器登录后，需要用户自行导出该站点的 Netscape Cookie 文件并主动导入；不会自动读取外部浏览器登录状态。第三方登录跳转仍通过此方式完成。

验证：97 项单元/集成、19 项授权桌面检查、类型检查和本地构建通过。桌面测试用独立 Session 的模拟 HTTPS 服务验证实际 Chromium 脚本请求、验证码子框架 302 跳转、外部主页面跳转限制、HTTP 403 诊断和固定浏览器地址，不仅调用策略函数。加密/登录完成流程继续使用合成凭据。匿名真实 X 登录表单可打开，但**未代用户输入真实密码，完整账号登录以及用户链接的下载仍需用户本人重试确认**；上述问题不被宣称为本次报错的唯一原因。
